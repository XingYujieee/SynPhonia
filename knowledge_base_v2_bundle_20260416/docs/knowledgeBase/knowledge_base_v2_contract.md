# 知识库模块 V2 接口与边界草案

## 1. 文档目的

本文档用于固化当前已经确认的知识库下一阶段开发方向。

它描述的是“下一轮实现应当对齐的目标契约”，不等同于当前代码已经完全实现的状态。

当前知识库代码仍以 v1 形态为主；后续代码重构、测试补齐、CLI 调整，应以本文档为主要依据推进。

## 2. 模块定位

知识库模块负责把一次次活动中产生的转录结果、总结结果和相关文件引用沉淀为可检索、可关联、可供前端灵活消费的结构化数据。

知识库模块不是以下能力的拥有者：

- 不负责生成转录文本
- 不负责生成总结文本
- 不负责规划前端页面的信息分区
- 不负责决定前端有哪些功能入口
- 不负责替代应用层创建活动文件夹

知识库模块负责的是：

- 接收一次完整活动的结构化输入
- 校验输入是否完整
- 存储活动记录
- 提供活动数据、文件引用、搜索结果、时间信息和关系数据
- 提供可被前端直接嵌入的知识图谱数据视图

## 3. 关于 “view bundle” 的定义

这里对 `view bundle` 做一个统一定义，避免后续讨论时含义漂移。

`view bundle` 指的是：

- 由知识库一次性打包输出的一整套前端视图数据
- 其中已经包含偏页面结构的块，例如导航区、历史区、详情区、时间线区、文件区
- 前端拿到之后，更像是在“直接消费一个已经分好区的页面数据包”

当前 v1 实现中的 `export_view_bundle(...)` 就属于这种思路。

它的优点是：

- 前期验证快
- CLI 导出后容易直接观察结果

它的缺点是：

- 容易把知识库和前端的信息架构绑死
- 容易让知识库越界承担“功能分级”和“页面分栏”职责
- 前端后续一旦改版，知识库输出也容易被迫跟着调整

因此，当前确认的方向是：

- `view bundle` 不再作为知识库未来的主接口形态
- 它可以保留为兼容层、调试导出层、或过渡期验证层
- 但知识库的正式主接口应改为“数据层输出 + 知识图谱视图输出”

## 4. V2 输入契约

### 4.1 必填语义字段

以下字段为上游模块必须提供给知识库的正式字段：

- `activity_id`
- `start_time`
- `end_time`
- `transcript_text`
- `summary_text`
- `summary_of_summary`
- `keywords`
- `keywords_of_keywords`
- `ppt_present`
- `activity_intro`
- `activity_name`

补充要求：

- 当 `ppt_present=true` 时，必须额外提供 `ppt_file_path` 或 `ppt_id`
- `start_time` 与 `end_time` 应至少精确到“年月日时分”
- `keywords` 与 `keywords_of_keywords` 应为上游已经整理好的关键词集合，而不是由知识库临时猜测

### 4.2 推荐同时提供的文件引用字段

为了支持本地文件预览、历史回看和后续模块装配，建议上游同时提供以下文件引用信息：

- `activity_dir`
- `transcript_file_path`
- `summary_file_path`

说明：

- 这里推荐采用“双轨输入”方案
- 即知识库同时接收“文本内容本身”和“对应文件路径”
- 这样既能保证知识库的搜索、关系计算和摘要预览不依赖外部文件即时读取，也能让前端或应用层直接使用本地路径做文件预览

### 4.3 输入校验与异常处理

这一点已经明确：

- `summary_of_summary`
- `keywords_of_keywords`
- `activity_name`
- `activity_intro`

这四个字段在目标契约中属于必填字段，不应再被当作可有可无的补充信息。

但知识库仍然必须做好异常处理。

推荐的校验行为如下：

- 若任一必填字段缺失，知识库应拒绝本次 ingestion
- 返回结果中应包含明确的异常状态，例如 `status=invalid_input`
- 返回结果中应明确指出缺失字段名列表，例如 `missing_fields`
- 如果字段存在但为空字符串、空列表或仅空白字符，也应按“缺失”处理
- 若 `ppt_present=true` 但既没有 `ppt_file_path` 也没有 `ppt_id`，也应返回明确错误

面向用户或上层协调器的要求：

- 错误信息必须能直接看出“缺了什么”
- 不能静默吞掉字段缺失
- 不能在缺字段时偷偷用推导值替代正式字段，再假装入库成功

### 4.4 字段兜底策略

为保证系统健壮性，可以保留兜底逻辑，但兜底逻辑不应掩盖正式异常。

推荐原则：

- 若缺少正式字段，先返回错误，再决定是否允许上层发起重试
- `activity_name` 可以在内部临时推导一个显示值用于调试，但不能把这个推导值视为正式入库成功
- `summary_of_summary` 和 `keywords_of_keywords` 不建议由知识库擅自生成

## 5. 输入来源与上层协调器职责

知识库不直接去旧模块内部拉数据。

正确的数据流应为：

1. 上游模块分别生成转录、总结和 PPT 相关结果
2. 应用层或上层协调器判断一次活动已经结束
3. 应用层在本地为该活动创建活动文件夹，并保存：
   - 转录文稿
   - 总结文档
   - 上传 PPT 的副本（如有）
4. 上层协调器汇总语义字段和文件引用字段
5. 上层协调器调用知识库 ingestion 接口

推荐的字段来源划分如下：

- 转录模块：
  - `transcript_text`
  - `transcript_file_path`
- 总结模块：
  - `summary_text`
  - `summary_of_summary`
  - `keywords`
  - `keywords_of_keywords`
  - `summary_file_path`
- 活动管理或应用层：
  - `activity_id`
  - `start_time`
  - `end_time`
  - `activity_name`
  - `activity_intro`
  - `activity_dir`
- PPT 相关模块：
  - `ppt_present`
  - `ppt_file_path` 或 `ppt_id`

## 6. 存储边界的调整方向

v1 的当前实现中，知识库会把转录文本和总结文本再写入自己的 workspace。

下一阶段建议调整为：

- 应用层负责创建并维护“每次活动对应的本地活动文件夹”
- 知识库以“接收现成的文本和文件引用”为主
- 知识库可以保留自己的索引、元数据、关系覆盖信息
- 但不再把“自己重新生成 transcript.txt / summary.txt”作为默认核心职责

这样做的好处是：

- 文件归属更清楚
- 前端做文件预览更自然
- 后续组装模块时，知识库不会抢占应用层的文件生命周期管理职责

## 7. V2 输出契约

### 7.1 核心数据输出

知识库的主输出应该是“数据层输出”，而不是“页面层输出”。

核心数据输出建议至少包括：

- 活动基础记录
- 时间信息
- 转录与总结文本预览
- 文件引用信息
- 搜索命中结果 
- 关键词信息
- 关系推断结果
- 人工关系修正结果

这些数据应当足够让前端自行决定：

- 是否按时间排列活动
- 是否展示转录预览
- 是否展示总结预览
- 是否提供文件预览入口
- 是否按活动类型做筛选

### 7.2 知识图谱视图输出

虽然知识库不负责做完整页面分级，但需要提供“最终知识图谱的可嵌入视图数据”。

因此，知识图谱是一个保留的明确输出能力。

建议该输出稳定包含：

- `nodes`
- `edges`
- 节点标题
- 关系强度
- 关系状态
- 关系原因

这样前端可以直接把图谱嵌入 UI，而不用重新做关系拼装。

### 7.3 不再作为主接口的输出

以下这类输出不建议继续作为知识库的长期主接口：

- 预设导航栏数据
- 已经分好功能区块的历史页数据
- 已经按前端页面结构拼好的详情面板

这些输出可以：

- 继续存在于兼容层
- 保留给 CLI 调试
- 用于过渡期演示

但不应再主导下一阶段的数据设计。

## 8. 前端消费方式

按当前确认的边界，前端更适合这样消费知识库：

- 读取全部活动记录
- 自行按时间排序
- 使用 `activity_name`、`activity_intro`、`summary_of_summary` 等字段构建列表卡片
- 使用 `transcript_file_path`、`summary_file_path`、`ppt_file_path` 触发本地文件预览
- 使用知识图谱输出直接渲染图谱区域

也就是说：

- 知识库负责“把数据准备好”
- 前端负责“把数据组织成什么页面功能”

## 9. 与当前实现的关系

当前实现与本草案相比，主要差异在于：

- 还没有正式接收 `summary_of_summary`
- 还没有正式接收 `keywords_of_keywords`
- 还没有正式接收 `activity_name`
- 还没有正式接收 `activity_intro`
- 仍然更偏向输出 `view bundle`
- 仍然默认自己落盘转录与总结文本

因此，本草案之后的开发重点应是：

1. 先改 schema 和接口文档
2. 再改存储与 service 输出
3. 最后补测试和 CLI 验证链路

## 10. 后续开发建议顺序

建议按以下顺序推进下一轮代码修改：

1. 调整 ingestion schema，使其支持新的必填字段和文件引用字段
2. 增加严格输入校验和明确异常返回
3. 调整存储层，弱化知识库自写文本文件的默认行为
4. 拆分“核心数据输出”和“知识图谱输出”
5. 将现有 `   bundle` 降级为兼容接口或调试接口
6. 补充测试，重点覆盖缺字段报错、文件引用、图谱输出和兼容层行为
